# Передача продукта заказчику (Customer Handover)

Документ описывает **текущее фактическое** состояние передачи сервиса «ПДн Контроль»
заказчику: что развёрнуто и кому принадлежит, какие настройки и внешние сервисы нужно
знать, как запускать/восстанавливать/проверять продукт, и с каких страниц начинать
эксплуатацию. Это не план на будущее, а снимок реального состояния; документ
поддерживается и обновляется по мере изменения доступов, деплоя и статуса передачи.

> Важно: секреты здесь не публикуются. Точные учётные данные, ключи и приватные
> инструкции доступа передаются заказчику и преподавателю через приватный канал
> (Moodle-сабмишн), а не через публичный репозиторий.

## Статус передачи

- **Уровень передачи (handover level):** `Deployed or operated on customer side` —
  продукт развёрнут и работает на **сервере заказчика** по адресу
  **https://pdn.neurolife.tech**; заказчик подтвердил, что эксплуатирует его у себя.
- **Статус подтверждения заказчиком (customer-confirmation status):** `Accepted` —
  заказчик принял инкремент `MVP v3` (`v1.3.0`) на встрече **2026-07-11**, признал
  документацию достаточной для самостоятельной эксплуатации и новых доработок не запросил
  (см. [`reports/week6/sprint-review-summary.md`](../reports/week6/sprint-review-summary.md)).
  Единственный оставшийся пункт передачи — перенос GitHub-репозитория — по договорённости с
  заказчиком выполняется **после окончания курса** (репозиторий нужен команде до завершения
  оценивания); это согласованный follow-up, а не открытый блокер.

## Что передано, делегировано и что осталось у команды

| Актив | Владелец / где | Статус |
|---|---|---|
| **Сервер / хостинг** | Заказчик (его инфраструктура) | Передан — продукт работает и эксплуатируется на сервере заказчика |
| **Домен `pdn.neurolife.tech`** | Заказчик | На стороне заказчика |
| **OAuth-приложения Яндекс / ВК** | Заказчик (его аккаунты) | Делегировано заказчику: интеграция реализована и проверена (UAT-08 на тестовом OAuth-приложении), боевые `client_id` / `client_secret` заказчик заводит и подставляет в `.env.secret` самостоятельно. Не блокирует остальной функционал |
| **E-mail: домен отправителя (SPF/DKIM)** | DNS-зона заказчика; записи подготовила команда | Готово — домен верифицирован, письма с кодом входа реально доходят (UAT-09, 2026-07-11) |
| **Почтовый провайдер (Resend)** | Аккаунт для отправки писем, ключ в `.env.secret` | Готово — работает на верифицированном домене заказчика |
| **Репозиторий кода** | GitHub `ValekusVachpekus/pdn-control` | Остаётся у команды на время курса и оценивания; перенос заказчику согласован и выполняется **после окончания курса** ([#131](https://github.com/ValekusVachpekus/pdn-control/issues/131)) |

## Конфигурация, внешние сервисы и секреты

Продукт конфигурируется через переменные окружения. Docker-стек читает секреты из
файла **`.env.secret`** (не `.env`); шаблон несекретных значений — `.env.example`.
Значения секретов заказчику передаются приватно.

Что нужно знать заказчику (без раскрытия значений):

- **LLM API-ключ (Qwen)** — обязателен; без него анализ политик/согласий не работает.
- **OAuth Яндекс / ВК** — `client_id` и `client_secret` приложений заказчика; задаются в
  `.env.secret`. Redirect URI приложений должен указывать на `https://pdn.neurolife.tech`.
  Заказчик заводит приложения в своих аккаунтах и подставляет ключи сам; после правки
  `.env.secret` нужен `docker compose up -d` для перечитывания окружения.
- **E-mail (Resend)** — API-ключ провайдера + верифицированный домен отправителя. Домен уже
  верифицирован: DNS-записи (SPF/DKIM) подготовила команда, заказчик прописал их в своей зоне,
  письма реально доходят. Без ключа сервис работает в DEV-режиме (код входа пишется в лог,
  письма не уходят).
- **Секрет подписи сессий/JWT** и **доступ к Postgres/Redis** — задаются в `.env.secret`;
  в проде не использовать значения по умолчанию.

Секреты в репозиторий не коммитятся. При утечке — немедленно отозвать/сменить ключ
(см. [`CONTRIBUTING.md`](../CONTRIBUTING.md) § «Секреты и чувствительные данные»).

## Запуск, восстановление и проверка

Продукт — монорепо из подсервисов, поднимается одним Docker-стеком на хосте заказчика.
Внешний доступ и TLS — через единый обратный прокси (см.
[ADR-0004](architecture/adr/0004-single-host-compose-caddy-tls.md)).

**Запуск / рестарт после перезагрузки сервера:**

```bash
cd backend
docker compose up -d        # поднять весь стек (backend + crowler + PDFreport + Postgres + Redis)
docker compose ps           # проверить, что все контейнеры healthy
docker compose logs -f      # смотреть логи
```

**Обновление до новой версии:** `git pull` нужного тега → `docker compose up -d --build`.

**Проверка работоспособности (smoke):**
1. Открыть https://pdn.neurolife.tech — грузится главная.
2. Зарегистрироваться / войти (e-mail-код или OAuth) — приходит письмо / отрабатывает вход.
3. Запустить проверку известного сайта — скан доходит до `done`, открывается отчёт.
4. Скачать PDF-отчёт — файл генерируется.

Точные приватные инструкции доступа к серверу (SSH, пути, учётки) передаются заказчику
и преподавателю в приватном канале.

## Достаточность документации и остаточная поддержка

Для достигнутого уровня (`Deployed or operated on customer side`) документация покрывает
запуск, рестарт, обновление, конфигурацию и smoke-проверку. На встрече 2026-07-11 заказчик
прошёл по набору документации и **подтвердил её достаточность** для самостоятельного запуска и
эксплуатации сервиса без участия команды. Единственная ремарка — не сразу понятно, где искать
документацию (репозиторий / GitHub Pages / Swagger); точки входа перечислены выше в разделе
«С чего начинать эксплуатацию».

Остаются открытыми к концу курса:

- **Production-ключи OAuth Яндекс/ВК** — заказчик подставляет свои `client_id` / `client_secret`
  самостоятельно (self-service, шаги описаны в разделе «Конфигурация»). Остальной функционал от
  этого не зависит.
- **Перенос репозитория заказчику** — по договорённости выполняется после окончания курса
  (репозиторий нужен команде до завершения оценивания)
  ([#131](https://github.com/ValekusVachpekus/pdn-control/issues/131)).

Ограничения после окончания курса: команда **не берёт на себя обязательства по поддержке и
развитию** сервиса; сервис не даёт юридической гарантии соответствия 152-ФЗ; работоспособность
AI-анализа зависит от действующего LLM API-ключа, который оплачивает и продлевает владелец
сервиса.

Открытые пункты передачи ведутся как задачи в milestone
[Sprint 7](https://github.com/ValekusVachpekus/pdn-control/milestone/5).
