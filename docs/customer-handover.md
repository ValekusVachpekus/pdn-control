# Передача продукта заказчику (Customer Handover)

Документ описывает **текущее фактическое** состояние передачи сервиса «ПДн Контроль»
заказчику: что развёрнуто и кому принадлежит, какие настройки и внешние сервисы нужно
знать, как запускать/восстанавливать/проверять продукт, и с каких страниц начинать
эксплуатацию. Это не план на будущее, а снимок реального состояния; документ
поддерживается и обновляется по мере изменения доступов, деплоя и статуса передачи.

> Важно: секреты здесь не публикуются. Точные учётные данные, ключи и приватные
> инструкции доступа передаются заказчику и преподавателю через приватный канал
> (Moodle-сабмишн), а не через публичный репозиторий.

## Статус передачи

- **Уровень передачи (handover level):** `Deployed or operated on customer side` —
  продукт развёрнут и работает на **сервере заказчика** по адресу
  **https://pdn.neurolife.tech**.
- **Статус подтверждения заказчиком (customer-confirmation status):**
  `Not yet accepted` — подтверждение запрашивается на встрече по готовности к передаче
  в Week 6. Будет обновлено после встречи (`Accepted` / `Accepted with follow-up items` /
  `Not yet accepted`).

> Актуальный итог передачи и подтверждение фиксируются также в
> [`reports/week7/README.md`](../reports/week7/README.md).

## Что передано, делегировано и что осталось у команды

| Актив | Владелец / где | Статус |
|---|---|---|
| **Сервер / хостинг** | Заказчик (его инфраструктура) | Передан — продукт работает на сервере заказчика |
| **Домен `pdn.neurolife.tech`** | Заказчик | На стороне заказчика |
| **OAuth-приложения Яндекс / ВК** | Заказчик (его аккаунты) | В процессе: заказчик заводит приложения и передаёт `client_id` / `client_secret` команде для настройки |
| **DNS-записи (e-mail: SPF/DKIM)** | Записи готовит команда, прописывает заказчик в своей DNS-зоне | В процессе: верификация домена отправителя |
| **Репозиторий кода** | Команда (GitHub `ValekusVachpekus/pdn-control`) | Пока у команды; передача/делегирование — по договорённости |
| **Почтовый провайдер (Resend)** | Аккаунт для отправки писем | В процессе: привязка к домену заказчика через DNS |

## Конфигурация, внешние сервисы и секреты

Продукт конфигурируется через переменные окружения. Docker-стек читает секреты из
файла **`.env.secret`** (не `.env`); шаблон несекретных значений — `.env.example`.
Значения секретов заказчику передаются приватно.

Что нужно знать заказчику (без раскрытия значений):

- **LLM API-ключ (Qwen)** — обязателен; без него анализ политик/согласий не работает.
- **OAuth Яндекс / ВК** — `client_id` и `client_secret` приложений заказчика; задаются в
  `.env.secret`. Redirect URI приложений должен указывать на `https://pdn.neurolife.tech`.
- **E-mail (Resend)** — API-ключ провайдера + верифицированный домен отправителя.
  Для верификации заказчик прописывает у себя DNS-записи (SPF/DKIM), которые готовит команда.
  Без ключа сервис работает в DEV-режиме (код входа пишется в лог, письма не уходят).
- **Секрет подписи сессий/JWT** и **доступ к Postgres/Redis** — задаются в `.env.secret`;
  в проде не использовать значения по умолчанию.

Секреты в репозиторий не коммитятся. При утечке — немедленно отозвать/сменить ключ
(см. [`CONTRIBUTING.md`](../CONTRIBUTING.md) § «Секреты и чувствительные данные»).

## Запуск, восстановление и проверка

Продукт — монорепо из подсервисов, поднимается одним Docker-стеком на хосте заказчика.
Внешний доступ и TLS — через единый обратный прокси (см.
[ADR-0004](architecture/adr/0004-single-host-compose-caddy-tls.md)).

**Запуск / рестарт после перезагрузки сервера:**

```bash
cd backend
docker compose up -d        # поднять весь стек (backend + crowler + PDFreport + Postgres + Redis)
docker compose ps           # проверить, что все контейнеры healthy
docker compose logs -f      # смотреть логи
```

**Обновление до новой версии:** `git pull` нужного тега → `docker compose up -d --build`.

**Проверка работоспособности (smoke):**
1. Открыть https://pdn.neurolife.tech — грузится главная.
2. Зарегистрироваться / войти (e-mail-код или OAuth) — приходит письмо / отрабатывает вход.
3. Запустить проверку известного сайта — скан доходит до `done`, открывается отчёт.
4. Скачать PDF-отчёт — файл генерируется.

Точные приватные инструкции доступа к серверу (SSH, пути, учётки) передаются заказчику
и преподавателю в приватном канале.

## Достаточность документации и остаточная поддержка

Для достигнутого уровня (`Deployed or operated on customer side`) документация покрывает
запуск, рестарт, обновление, конфигурацию и smoke-проверку. Остаётся необходимой
поддержка на время финализации передачи:

- завершить настройку **production-OAuth** на ключах заказчика (Яндекс/ВК);
- завершить **верификацию e-mail-домена** (DNS-записи прописывает заказчик);
- согласовать судьбу **репозитория** (остаётся у команды / передаётся / делегируется);
- получить **подтверждение заказчика** о достаточности этого документа (Week 6/7).

Открытые пункты передачи ведутся как задачи в milestone'ах
[Sprint 6](https://github.com/ValekusVachpekus/pdn-control/milestone/4) и
[Sprint 7](https://github.com/ValekusVachpekus/pdn-control/milestone/5).
